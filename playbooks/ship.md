# Ship

**You own what lands. Land one PR at a time, each only after it clears the gate for its risk, then keep your hands off.** Rigor follows risk: a Low PR needs green CI and its review; a High PR also needs a verdict from a verifier who didn't write it. Merging without a yes on each PR is allowed only where the router's rule 2 allows it (mode `auto`, or `shinstack-mode.merge: auto`). Otherwise stop at **verified and green** and hand the PRs to the user; nobody pushes after the handoff without a go.

**Common case:** the user or the PR says it is approved and CI is green, and the tier is None, Low or Moderate. The forge's approving review decision counts as the review. Check state and CI once, then run `gh pr merge <pr> --squash --match-head-commit <sha>` and read it back. If one `gh pr view` shows no head SHA, merge unpinned and say so; don't hunt for it. Take the forge CLI's answers as given: don't fetch the diff, inspect the CLI, git remotes or branches, or hunt for evidence the gate below doesn't ask for.

**The gate.** Take the PR's tier from the review table in `opening-a-pr.md`. An unclear tier goes up.
- *None, Low or Moderate:* at the current head, green CI (with no CI, run the repo's checks and paste the output), the review its tier names (an empty one counts as not run, see `opening-a-pr.md`), and no open blocking finding. It needs no verifier.
- *High:* all of that, plus a verdict from an independent verifier (below).
- *Any tier:* check the PR for a verdict. The latest one must be `PASS` or `PASS+NOTES` and must still describe the code (step 3). A `FAIL` stops the merge until a newer verdict replaces it, whatever was pushed since.

**A merge the user approved** (a yes in a mode that would otherwise ask; not the common case above, where the repo is `auto` and the forge shows the PR approved). In any mode, a user's explicit yes on one PR replaces the numbered steps, so a hand-built PR needs no verdict file. A PR that has a verifier still needs `PASS` or `PASS+NOTES` at its current head.
- Before merging, check for anything the user may not know: a commit pushed after their approval, red CI (if the repo has CI), an open blocking review finding, a required review that was empty or not run, a missing or failed verdict, or a High-risk PR with no verdict. Run step 4's trunk check too. If you find any of these, stop and say what you found. A yes given after you flagged an empty or not-run review is final for that head on that point only; one given before you flagged it isn't, and every other finding needs its own yes. A rebase changes the head, so it needs a new yes.
- Merge that one PR, pinned to the head you checked (`gh pr merge <pr> --squash --match-head-commit <sha>`, or the forge's equivalent). If the forge returns no head SHA to pin, merge unpinned and say so; a missing pin is not a reason to stop. Another PR needs another yes.
- Read back the PR's state, merged time and base, and name the merged SHA in your reply. If the base isn't trunk, say the change hasn't reached trunk. If the PR closes an issue that is still open, say so.

## Verifier (owner, verifier, merge-ready)

**You own the verdicts, never the PRs. One owner carries each PR; nothing is merge-ready until a verifier who didn't write it has proven the code at its current head.** Use it when a High-risk PR will merge unattended, or when the user asks.

1. **Check the mode and the limits first.** Items the user keeps for themselves, and PRs outside the queue, stop at merge-ready. Never type credentials, never touch sensitive personal data.
2. **One owner per PR** (a builder, standard weight), in its own worktree off trunk. The owner's brief states the tier, its required review, the paths it may write, the actions it must not take and that subagents are allowed (`coordinate.md` kickoff). It builds under the playbook that fits (`feature.md`, `bug-fix.md` or `refactoring.md`), opens the PR early so CI runs alongside, rebases onto current trunk, then reports the **code-ready head**. Run PRs in parallel off trunk, never stacked, unless one truly builds on another (then base it on that branch). The owner commits and pushes each finished unit before starting the next, so a replacement can resume.
3. **Verify once, independently, at the code-ready head.** The verifier (strong weight), a fresh-context subagent that never saw the author's reasoning, briefed with the PR, the tier, that subagents are allowed and that it posts its own verdict (step 5), reruns the repo's gates (lint, typecheck, tests, mutation survivors), reads the linked issue or spec and its comments, proves the load-bearing behavior and the issue's Done when against the running thing (whatever the heading, run the behavior, never grep for a sentence; with `Refs #N`, only the items the PR's `## Scope` claims; with no Done when, set `done_when` to `none`) and tries to break it for risky changes (`/shinstack:blast-radius`, `/shinstack:interrogate`). It tests Done when as written, plus later comments from outside the run (the user, or the issue's author if a person). A comment from the PR's owner or any agent in the run never narrows it. Re-verify only for new behavior or a large new diff; a rebase or minor fix gets a single check at the new head; a wording-only change gets none.
4. **Block only on what you can show:** a failing run at the head, a bug a user would hit, a failed gate, an unmet Done when item from step 3, or a doc line the PR made wrong. A problem the base already has doesn't block unless the PR copies or newly reaches it. Everything else becomes a follow-up.
5. **Verdicts are files, not sentences.** Write `{pr, head_sha, verdict: PASS|PASS+NOTES|FAIL, evidence: [commands and outputs], done_when: [{item, PASS|FAIL}] or "none"}` (any `FAIL` item makes the verdict `FAIL`) and have the verifier post it as a comment on the PR, in exactly that JSON, so any session can find it. The verifier posts it itself. An owner who receives a prose verdict sends it back to the verifier to post (or, if that verifier is gone, starts a fresh verifier at the same head), and never writes or transcribes a verdict: all agents share one GitHub account, so a check can't tell who wrote it. A verdict covers one head SHA, so a new push needs a new verdict. Green CI alone is never a verdict.
6. **Loosening a gate needs proof and your countersign.** A raised budget or an allowlist entry needs the verifier's proof first, because the owner is the one who wants green. A disabled or soft-failed check always comes out.
7. **Audit on a heartbeat** while delegated work remains: arm the recurring poll yourself, probe every agent by its side effects (pushes, commits), and treat an agent as stuck if it errors or shows nothing new past its expected runtime. A hold from the user reaches every owner as a zero-writes order.

**Make it enforceable (factory):** gantry's `sf-verdict-check` gate schema-validates the verdict and won't mark a PR merge-ready unless its `head_sha` equals the PR's current head.

## Landing

1. **Clear the gate for each PR before it lands.** Where the gate needs a verdict, it is a comment the verifier posted itself (never the author, even transcribing), at the PR's current head. If the author posted or transcribed it, treat it as missing.
2. **Land only the contiguous cleared run rooted at the bottom.** For stacked PRs, walk up from the lowest unmerged PR and stop at the first that hasn't cleared its gate. A cleared PR above an uncleared one waits. A PR whose branch neither holds nor needs the lower code may move onto trunk and land on its own.
3. **Re-check that each verdict you rely on still describes the code.** A rebase moves every PR above it to a new SHA without failing a check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. A difference only in tests, docs or lint config can stand if what it ran builds the same at both.
4. **Merge right, then read it back.** Right before merging, fetch trunk and ask whether its changes can affect the patch. Rebase and wait for CI only when the code that would land was never tested (a conflict, a file both sides changed). Merge the lowest unmerged PR, pinned to the head you checked (`gh pr merge <pr> --squash --match-head-commit <sha>`, or the forge's equivalent). Confirm with the PR's state, merged time and base.
5. **Leave the stack alone while it lands.** Moving the next PR to trunk is the only change to a branch or base. Watch the run with a Monitor or ScheduleWakeup, not "I'll check back", until it reaches the ceiling.
6. **Stop at the ceiling.** Extending the run means the next PR has to clear its gate first.

**Make it enforceable (factory):** the merge step is the factory's `sf-ship` gate. It reruns gantry's `sf-gate-evidence` and `sf-verdict-check`, so it refuses on a `FAIL`, on a verdict whose `head_sha` is not the branch head, or where the tier needs a verdict and none exists. It merges only where the repo's `shinstack-mode` is `auto`; otherwise it parks the PR.

**Reply:** the cleared run and its ceiling, each PR's tier and gate result, any verdict and who produced it, what landed and how you confirmed it, what is ready, gates waiting on the user, and what the next gap needs.
