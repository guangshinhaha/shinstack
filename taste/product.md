# Product taste

Shin's product calls, inferred from past decisions; strong defaults, not law. Loaded by `brainstorm` and when writing or grooming an issue (rule 11 in #68). Each line: the trigger, the call, why.

- **Aggregate, Not Individual, Analytics** (when asked for analytics about the people using or served by the product): Ship the aggregate or group-level cut and refuse the per-person one, even when the data exists. "Mondays have 30% more absences" is operational insight; "person X was absent 8 times" is surveillance and kills adoption.
- **Capture the Live System as the Spec** (when rebuilding a system another team owns): Derive the ticket from a dated capture of the live system with screenshots, and record where it contradicts the written spec. The written spec drifts; the running system is the truth.
- **Close and Refile** (when a ticket's premise is wrong, duplicated or in the wrong place): Close it and refile the true residue narrowly, carrying surviving scope across in writing. Don't edit it into a different ticket. History stays honest and the new ticket starts from verified facts.
- **Coverage Over Polish** (when zero-to-one work): Optimise for how many distinct problems you touch, not how well any one solution is built. Early on, finding which problems matter beats perfecting one answer.
- **Crude Interim When the Date Is Fixed** (when the right architecture has unknown effort and the date cannot move): Ship the crude mechanism, cover the failure mode with training or documentation, and defer the architecture. Throwaway user friction is cheap to absorb; throwaway engineering is not.
- **Default Framework Only If You Own the Shell** (when picking a framework for a new product): Use the team's default only when the product is the application, not when it is a module mounted in a host that already owns routing, layout and auth. The default carries conventions that fight the host.
- **Defer Rather Than Ship Degraded** (when a partner's delivery is broken and the surface is highly visible): Defer the integration until their prerequisite exists instead of shipping the workaround. A bad first impression on a visible surface costs more than waiting.
- **Demo First** (when an inbound team asks to be onboarded): Show the demo before any bespoke work, and onboard second. The demo shows whether the fit is real before effort is spent.
- **Design Wider Than Build** (when designing a pattern that will have more than one use): Design the full pattern across every foreseeable use case, then build only the first slice. Covering the cases up front means later slices don't force rework.
- **Do Not Invent Evidence** (when submitting evidence to clear a gate): Run the check or say it wasn't run. Never produce a record shaped like proof for something that didn't happen. A schema-valid record for a script that never ran is worthless.
- **Engineers During Design** (when a design is being shaped for a fixed ship date): Put engineers in the design loop while design is happening, and let the ship date constrain design. A design that cannot ship by the date is not finished.
- **Explicit Out of Scope** (when writing or grooming a ticket): Every ticket lists what it excludes. Name the adjacent work it does not include. Unstated scope is where estimates and reviews go wrong.
- **External LLM Out of Sensitive Codebases** (when an AI step would call an external model vendor from inside a sensitive codebase): Move the step to a local tool that emits an artefact the existing deterministic path already accepts, even if the integration is built and reviewed. It removes the outbound call and review burden while keeping the deterministic path unchanged.
- **Honesty Must Not Cost the User's Work** (when showing a user an error after they put in effort): Tell them what failed, and keep what they entered on screen. Transparency that also discards their draft is a failure of its own.
- **Lower Fidelity for Leadership** (when preparing a prototype for a decision session): Cut prototype fidelity and lead with a before-and-after journey. High-fidelity detail invites nitpicks on click depth instead of a decision on the concept.
- **Middle Option for Tiny Populations** (when a case affects well under 1% of users): Neither cut it nor build it properly. Ship an acceptable-not-good experience and name the date the good version is revisited. Capacity is better spent on the main flow, and a dated revisit stops the compromise from becoming permanent.
- **Name It or Close It** (when a rollout or pipeline item has no named, committed counterparty): Close it instead of keeping a placeholder open. Reopen if it becomes real. Placeholders create the look of progress and hide what is actually planned.
- **No Criterion Satisfiable by a Sentence** (when writing an issue's Done when or acceptance criteria): A criterion that can be passed by rendering the right words is a bad criterion. Require something that actually does the thing. Every stage can pass it honestly and nothing is tested.
- **No Route for Indirection** (when tempted to add a page whose only job is a stable address or a role variant): Use a redirect or a tab inside the existing view instead. Each route is surface area to maintain.
- **Optimise for the Next Maintainer** (when choosing between designs or conventions): Choose the version that survives handover to someone who wasn't in the room. What works for the people who built it often breaks for the next person.
- **Own Repo and Database From Day Zero** (when a new capability could plausibly become its own product): Give it its own repository and database, and have the incumbent reach it over an HTTP contract, never a shared schema. Separation is enforced by the structure, not by discipline.
- **Platform the Easy Half** (when two products build the same concept): Pull it to the platform layer, ship the easy shared half, and defer the part that makes them genuinely different. Shared work is cheaper once, but forcing the differences into one abstraction too early is costly.
- **Publish the Delta** (when a ticket's decision or scope changes after grooming): Post what changed, why, and which open questions it closes as a comment. Don't silently rewrite the body. The change stays traceable and reviewers don't re-read the whole ticket to find it.
- **Readiness Gates** (when onboarding several groups to a launch): Gate onboarding on a few yes/no checks and launch the ready ones on time instead of waiting for the slowest. One slow group should not hold everyone back.
- **Reject AI That Needs Data Users Don't Produce** (when evaluating an AI feature whose accuracy depends on input data): Reject it if users don't already produce that data as a by-product of their work. Making it accurate means users key in extra metadata, adding the workload the product exists to remove.
- **Resolve Privilege Downward** (when identity data is ambiguous or a user changes context): Resolve to the least privilege and make them re-earn the rest. Refuse convenience that weakens an auth invariant. Resolving upward is exactly the failure that least privilege exists to prevent.
- **Revert Whole Feature When Blocked** (when shipped code blocks a pilot's primary flow and the fix is outside your control): Revert the whole feature within a day. Don't patch, gate or wait on another team. A clean revert is the fastest safe rollback.
- **Security Triage by Reachability** (when a security or correctness finding lands on code no live user can reach): Close it as not planned with a named re-open trigger. Don't fix it, and don't leave it in the backlog. Effort goes to live risk, and the trigger brings the finding back when it becomes reachable.
- **Split Integration From Evaluation** (when a story mixes making something work with measuring how well it works): Separate "make it work" from "measure whether it works well" into different stories, and do not gate the first on the second. Shipping the integration first gives you something real to evaluate. Formal evaluation comes after.
- **Unknown Is Never Free** (when the system cannot tell "nothing here" from "we do not know"): Add the third state and fail loudly. Never let missing data resolve to the permissive or optimistic default. Under-promising is cheaper than a confident wrong answer.
- **Workflow Fix Before Reimagining** (when offered a small workflow fix and an ambitious rethink): Build the workflow fix first and treat it as the platform the ambitious version needs. The fix proves value sooner and lays the foundation the rethink would need anyway.
